## 二、Findings

**F-1【P0｜BLOCKING】需求分量①无完整实施承载——HD-002/003/004 三条 breaking 无批次、无完成判据，「恢复可用」无直接验收路径**

- 问题：设计 R0~R5 六批中零批承载 settings 声明制迁移（HD-002）、codec create() 迁移（HD-003）、addAttachments 迁移（HD-004）的产品代码修复；设计引用的「0.2.0 适配任务」（DEC-5/§6 表头）在 tracker 无独立行——悬空引用。若 Coordinator 直接采纳 R0~R5 为实施链，分量①（也是分量③的前提——插件不修 HD-002/003 就无法在 0.2.0 上加载，更谈不上发布）整体落空。两产出作为「双产出合流」的审查对象，用户目标第一分量到实施批的映射链断裂。
- 建议：合流时显式补适配批定义（建议 A1 装载门验证/HD-001 收口、A2 HD-003、A3 HD-002（含 T-3 验证前置）、A4 HD-004），每批给判别性红绿验收门 + 与 R 批依赖序（A2/A3 须先于 R2 的徽章真机截图）；或在实施链立案文件中显式映射 HD-* → 批次，消灭「0.2.0 适配任务」悬空引用。这是 NEEDS_CHANGE 的唯一判定锚点。

**F-2【P1】「插件在 0.2.0-rc.2 下恢复加载」缺机器侧直接判据；R2「真机面板截图」与"发布前仅机器侧验证"约束的口径未定义**
- 位置锚点：设计 `§6 R1 验收门`（"npm/pnpm 安装面冒烟"——协议未定义）、`§6 R2 验收门`（"真机面板截图证据（P10-③）"）；任务约束（插件已卸载，发布前仅隔离冷装/测试网，真机复验后置重装后）
- 问题：HD-001 修复效果的唯一直接判据（宿主装载门放行、无 skip）在任何验收门中都不存在；R2 的"真机"在发布前语境下指向不明（本机隔离 profile 冷装是否算数未定义）。
- 建议：R0 或 A1 批验收门补「隔离冷装装载门」：沙箱 profile + 0.2.0-rc.2 宿主 + 断言装载日志无 `skipping profile bundle "dsh-agent-router"`；同时定义 R2 截图的本机隔离冷装取证口径，真机复验清单留位到重装后（与 F-7 合并处理）。

**F-3【P2】两产出同树同日一手读数冲突：schemastery 3.18.4（diff 清单）vs 3.18.5（设计 F-B）——本审查重读仲裁 = 3.18.5**
- 位置锚点：diff 清单 `取证树表`（"cordis 4.0.5 + schemastery 3.18.4"）+ `§7`（HOST_BASELINE 刷新建议值 `schemastery:'3.18.4'`）；设计 `F-B`（实测 3.18.5，声明 ~3.18.4 范围内装到 3.18.5，明示"以一手为准"）；本审查实读 `C:/Users/peter/AppData/Roaming/npm/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/schemastery/package.json` = **3.18.5**
- 问题：diff 清单是自称的「后续适配实施批的事实基线」，其 §7 建议值若被 R0 直接消费，HOST_BASELINE 将锚到错误值（快照测试对实读树断言即红）。P1-fact-risk：设计侧已显式标注冲突（合规），清单侧未 reciprocate。
- 建议：R0 开工时单点重读定谳并以 3.18.5 为准；顺带核对该读数漂移是否因全局树当日被宿主自更新（若是，即 FIX-003 族的现场新证，可入风险登记）。

**F-4【P2】蓝军第 1 轮 B 格叙述混淆两个失效 regime——minor 跳位（0.3.0）下插件被宿主硬门 skip，三态徽章/降级信封均不可达**
- 位置锚点：设计 `§4 第 1 轮 B 格`（"用户已在 unknown 态运行——三态徽章使其可见"）+ `§7.2 风险表`首行（雷达窗口期缓解 = 三态徽章）
- 问题：DEC-1 选单范围 `^0.2.0-rc.2`（0.x caret = `>=0.2.0-rc.2 <0.3.0`，宿主门控 includePrerelease）：patch/预发布（如 0.2.1-alpha.5）过门 → unknown 态可运行、徽章可见，叙述成立；但 minor 跳位（0.3.0）过不了门 → 插件整层 skip、插件侧一切可观测机制不可达，该 regime 的 fail-observable 实际靠宿主自身 skip 警告（HD-001 已实录其 stderr 形态）。设计未区分这两个 regime，导致「避免每次升级插件都会失效」的用户期望管理不准确（minor 跳位窗口期内插件仍是全失效，检测到的是雷达/宿主警告而非插件徽章）。不改变 B 优于 A/C 的结论。
- 建议：设计补「gate-block vs gate-pass-unknown」两 regime 的显式区分；SOP 第 1 步与 README 矩阵照此口径表述。

**F-5【P2】雷达查询规格对预发布通道失明——宿主以 rc/alpha 快速迭代是既定事实（用户实跑 rc，npm 已有 0.2.1-alpha.5 流动）**
- 位置锚点：设计 `§2-B 四维-c 雷达`（`npm view @deepseek-ai/dsh version`）+ `DEC-3`；蓝军第 1 轮直接推演 0.3.0，未覆盖「0.2.1-alpha 已在流动」
- 问题：`npm view <pkg> version` 默认取 latest dist-tag——alpha/rc 若挂独立 tag 则雷达不可见；而宿主迭代节奏（本次用户环境 0.1.5-rc.2→0.2.0-rc.2、registry 已有 0.2.1-alpha.5）证明预发布通道就是实际部署通道。
- 建议：雷达查询改枚举 dist-tags（至少 latest + 预发布 tag 集合），DEC-3 扩展该项裁决。

**F-6【P2｜P10-⑤-violation】验收路径无用户使用视角基础场景位**
- 位置锚点：设计 `§6 各批验收门` 全表 + `§2-B 四维-d SOP`；diff 清单 `§2 HD-002`（settings 换代——老配置读取/热同步/持久化恰为高危面）
- 问题：老会话跨宿主升级重开、重启恢复、快速连续操作、目标值=默认值四类基础场景在两产出的验收路径与重装后复验约定中均无位置。HD-002 迁移（document 语义/revision/volatile 写入门/四个热同步消费者）正是这些场景的集中暴露面；T-5 只覆盖事件时序不覆盖重启恢复。
- 建议：适配批（A3）验收门与重装后真机复验清单显式纳入四场景（至少：0.1.5 时代老配置在 0.2.0 下可读可写、stats 持久化跨重启、设置变更后热同步不依赖重启）。

**F-7【P2】重装后真机复验清单无留位**
- 位置锚点：设计 `§2-B 四维-d SOP 第 5 步`（一句"装回真机复验顺延"）+ tracker（FIX-052/FIX-049 顺延同口径）
- 问题：分量③的用户可见最终验收路径只有"顺延"约定，无清单条目/模板留位——后置不等于不留位，否则发布时复验范围不可核。
- 建议：R5（SOP 固化批）复验清单模板中留「重装后真机复验」节，条目来自 F-2/F-6。

**F-8【P3】发布链 CHANGELOG 要素零承载**
- 位置锚点：两产出全文（"CHANGELOG" 0 命中）；repo 根存在 `CHANGELOG.md`（v0.4.5/v0.5.0 发布惯例实证）
