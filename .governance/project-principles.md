> **版本**: P-v2（2026-08-23 升级）· **来源**: 用户会话指令（/governance 2026-08-20 恢复面板自定义答复，DEC-016 入账 / GOV-001 执行）+ 2026-08-23 用户指令"需要升级约束"（DEC-022 入账，四项全选）
> **性质**: 本项目全部任务（分析/设计/实现/修复/发布）的强制行为准则。与治理工作流（software-project-governance）叠加生效；两者冲突时以更严格者为准。

## 一、原则（7 条）

| # | 原则 | 执行锚点（本项目既有机制 / 先例） |
|---|------|----------------------------------|
| P1 | 分析和推演需要基于事实，不允许假设和编造 | evidence-log 证据链；V-DSH 待验证清单（无实证不泛化——DEC-014 先例）；not-measurable 不编造（EV-023 metrics 红线） |
| P2 | 实现需要进行全面的分析，避免修改遗漏 | 变更影响分析（change-impact 五步）；架构 §8 分步迁移路径（依赖链显式化）；Reviewer 设计一致性逐项核验 |
| P3 | 实现需要考虑对原有功能的影响，避免引入新问题 | 回归断言零回退纪律（534 smoke 基线）；每次审查含"既有断言全部保持"核验（EV-011~023 通例） |
| P4 | 实现需要进行测试看护，构建防护网，避免后续问题反复 | DEV-002（核心通路自动化测试补强）；RISK-001（CI 缺口跟踪）；tests/metrics.mjs 31 项观测；返工后必须复跑全量（EV-014/021 先例）。**P-v2 强化**：产品代码变更 MUST 运行全量测试网（smoke 856/routing-paths 102/stats 99/metrics/parity/credentials 零回退）且命令汇入门控脚本（npm test 等价物），禁止以"只改了 X"为由跳过全量——RISK-001 主轨道（当前无 CI 全靠纪律，升级为机制） |
| P5 | 实现需要考虑泛化性，严禁单点修改 | DEC-005 通用附件路由框架（模态无关设计）；M2 统一编址层（非图片特化）；模态矩阵 audio/video 留位（Step 7） |
| P6 | 以高质量交付为准则，严禁为了完成任务而忽略质量 | Gate 体系（G1-G7）；独立审查链（R1-R14，含两次 NEEDS_CHANGE→返工→复审闭环先例）；D-1 验收门；关闭规则"P1 有遗留计划→有条件通过" |
| P7 | 修复要保证安全性，避免引入导致损坏用户数据的情况 | fail-closed 边界（R12 F-1 符号链接逃逸防护）；内容寻址完整性校验（sha256 往返，EV-017）；O_EXCL 写入不覆盖 + 碰撞去重（R10 F-02）。**P-v2 强化**：数据删除/覆盖路径 MUST 具备不可逆保护（原子写/软删除/凭据冗余删除）+ **旁路路径判别测试**（所有入口到达同一安全路径——W-5 三层防线先例：通用区过滤→deleteOauthAccount 分流→服务端成员校验；R7-F1 旁路导致活 refresh token 残留的教训） |
| P8 | 失败与降级 MUST 可观测——任何失败/能力判定缺失/降级路径 MUST 产生明确诊断事件或错误信息，禁止无观测吞错 | **P-v2 新增**。锚点：R2-F3 record 吞错零观测（selfReport 八计数无一覆盖 record 路径）；FIX-003 预检静默拒绝（service.js:1174 能力判定失败无观测）；selfReport 计数完备性（每次 catch MUST 有对应观测通道）；对等先例：C-9 oauthEvents 环形缓冲 + P7 零 token 断言 |
| P9 | 宿主演进防御——对宿主（dsh-llm/pi-ai/dsh-attachment）接口与能力判定的依赖 MUST 具备能力自证或 parity 守卫，禁止单向信任宿主行为 | **P-v2 新增**。锚点：RISK-003（宿主演进两次实证——FIX-001 prepareCall 缺失（parity 守卫先例）；FIX-003 能力判定收紧（pi-ai DEFAULT_INPUT=["text"] 致 text-only）；FIX-004 承接落地（能力自证/预检可观测/热载替代评估）；README L125 实测事实（qwen3.7-plus 可看图——插件自证信息来源） |

## 三、落地机制（如何在会话中生效）

1. **AGENTS.md 投影**：DSH 每会话自动注入「项目质量原则」段（本文件为权威源，投影仅为携带通道）
2. **会话 bootstrap**：读取 plan-tracker 时经版本规划纪律条款引用本文件（发布复盘演进检查）
3. **审查检查面**：Code/Design Reviewer 将本原则表纳入审查维度——违反原则的实现 MUST 在审查结论中标注违反条目（如 `P4-violation`、`C4-violation`）；P-v2 起 P8/P9 为必查维度
4. **执行包约束**：活跃产品代码任务的 execution-packet 应引用相关原则条目作为完成定义的一部分（Check 18c 范围校验）；P4 门控命令引用随执行包下发
5. **门控机制（P4）**：全量测试网命令（`node tests/smoke.mjs` + routing-paths + stats + metrics + parity + credentials）为产品代码变更的提交前默认门控；CI 就绪（RISK-001）后升级为自动门控

## 四、持续改进与扩充约定

1. **演进时机**：复盘会议（阶段 11）/ Gate 评审 / 任何会话中用户或 Reviewer 提出
2. **入账协议**：新增或修改原则 → decision-log 记录（DEC-xxx，含理由与影响面）→ 本文件更新（P-v1 → P-v2，变更历史表追加）→ AGENTS.md 投影同步
3. **质量基线只升不降**：任何修改不得削弱既有原则的约束力；替换条目需给出等价或更强的约束
4. **扩充方向（候选，按需入账）**：性能基线、可观测性规约（P8 已立——剩余：文档规约、安全审计清单）
5. **复盘强制检查**：每次版本发布复盘时 MUST 检查本文件是否需要演进（plan-tracker 版本规划纪律已挂钩）
